Understanding Lifetimes in Rust

A comprehensive, step-by-step guide — from easy to hard — with runnable examples.

1. Introduction & The "Why"

Lifetimes are Rust's answer to one of the hardest problems in systems programming: how do you guarantee that a reference never points to freed memory? In languages like C and C++, this is left to the programmer. Get it wrong and you get a use-after-free — undefined behavior, silent corruption, or security holes. In Rust, the compiler checks this for you at compile time, with zero runtime cost. The mechanism that makes this possible is called lifetimes.

A lifetime is not a thing that exists at runtime. It is a compile-time label that the borrow checker uses to reason about how long a reference is valid. You can think of a lifetime as answering the question: "For what region of the program is this reference guaranteed to point to live, valid memory?"

1.1 Why We Need Lifetimes: The Dangling Reference

Let's start with the problem lifetimes solve. Consider this code that tries to create a dangling reference — a reference to memory that has already been freed:

src/main.rs — This does NOT compile
fn main() {
    let r;                // ---------+-- 'a  (r is declared here)

    {
        let x = 5;        // -+-- 'b  |     (x is declared here)
        r = &x;           //  |       |     (r borrows x)
    }                     // -+       |     (x goes out of scope — freed!)

    println!("r: {r}");   //          |     (r is used here — but x is gone!)
}                         // ---------+

Here's what happens when you compile this:

Compiler error
error[E0597]: `x` does not live long enough
 --> src/main.rs:5:13
  |
5 |         let x = 5;
  |             - binding `x` declared here
6 |         r = &x;
  |             ^^
  |             |
  |             borrowed value does not live long enough
7 |     }
  |     - `x` dropped here while still borrowed
8 |
9 |     println!("r: {r}");
  |                  ---
  |                  borrow later used here

For more information about this error, try `rustc --explain E0597`.

The compiler is telling us: x (lifetime 'b) is dropped at line 7, but the borrow of x (stored in r, which has lifetime 'a) is still used at line 9. The borrow checker compares these two lifetimes and finds that 'b is shorter than 'a — the reference outlives the data. This is rejected.

Key Insight The borrow checker doesn't run your code. It compares scopes (regions of code) statically. If a reference's scope is larger than the data's scope, it's a dangling reference and the code is rejected — before the program ever runs.

1.2 The Borrow Checker

The borrow checker is the part of the Rust compiler that verifies all borrows are valid. Its job is simple to state but profound in effect:

  • Every reference has a lifetime — a region where it's valid.
  • Every piece of data has a lifetime — a region where it exists.
  • A reference's lifetime must not exceed the data's lifetime. (The reference must not outlive what it points to.)

When the borrow checker sees a function that takes references and returns a reference, it needs to know: which input is the output borrowing from? This is where lifetime annotations come in — they describe the relationship between input and output lifetimes so the borrow checker can verify correctness at every call site.

┌─────────────────────────────────────────────────────┐ │ THE BORROW CHECKER'S JOB │ │ │ │ data lifetime: [████████████████] │ │ ref lifetime: [████████████████████████] │ │ ▲ │ │ ERROR! ref out- │ │ lives data │ │ │ │ data lifetime: [████████████████████████] │ │ ref lifetime: [████████████████] │ │ ▲ │ │ OK! ref is within data's life │ └─────────────────────────────────────────────────────┘

2. Lifetimes You Already Have (Elision Rules)

Here's the good news: most of the time, you don't write lifetimes at all. The compiler has a set of rules — called lifetime elision rules — that automatically insert lifetimes into your function signatures. You've been benefiting from these rules since your first Rust program, even if you didn't know it.

When you write this:

What you write
fn first_word(s: &str) -> &str {

The compiler silently rewrites it into this:

What the compiler sees
fn first_word<'a>(s: &'a str) -> &'a str {

There are three elision rules, applied in order. Let's walk through each one.

2.1 Rule 1 — Each Input Reference Gets Its Own Lifetime

The first rule says: every reference parameter that doesn't have an explicit lifetime gets a fresh, unique lifetime.

Rule 1 in action
// You write:
fn foo(x: &str, y: &str) { ... }

// Compiler applies Rule 1 — each input gets its own lifetime:
fn foo<'a, 'b>(x: &'a str, y: &'b str) { ... }

Each & without a lifetime gets a distinct 'a, 'b, etc. They are not the same lifetime — the compiler treats them as independent until a later rule connects them.

2.2 Rule 2 — Single Input Lifetime Goes to All Outputs

The second rule says: if there is exactly one input lifetime parameter, that lifetime is assigned to all output (return) lifetimes.

Rule 2 in action
// You write:
fn first_word(s: &str) -> &str { ... }

// Step 1 (Rule 1): input gets a lifetime
fn first_word<'a>(s: &'a str) -> &str { ... }

// Step 2 (Rule 2): only one input lifetime, so it goes to output too
fn first_word<'a>(s: &'a str) -> &'a str { ... }

This makes intuitive sense: if a function takes one reference and returns a reference, the output must be borrowing from the input (it can't borrow from anything else). So tying them together is always correct.

2.3 Rule 3 — In Methods, &self's Lifetime Goes to Outputs

The third rule applies to methods (functions with a self parameter). It says: if there are multiple input lifetimes, but one of them is &self or &mut self, then the lifetime of self is assigned to all output lifetimes.

Rule 3 in action
impl<'a> ImportantExcerpt<'a> {
    // You write:
    fn announce_and_return_part(&self, announcement: &str) -> &str {
        println!("Attention please: {announcement}");
        self.part
    }

    // Compiler applies all 3 rules:
    // Rule 1: &self -> &'b self, announcement: &'c str
    // Rule 2: doesn't apply (more than one input lifetime)
    // Rule 3: &self exists, so output gets self's lifetime ('b)
    fn announce_and_return_part<'b>(&'b self, announcement: &'c str) -> &'b str {
        self.part
    }
}

This also makes sense: a method returning a reference is almost always returning something borrowed from self, not from one of its other arguments.

2.4 When Elision Fails — You Must Be Explicit

If none of the three rules can determine the output lifetime, the compiler gives up and asks you to write the lifetimes explicitly. This happens in two common situations:

Illegal elision — no inputs to infer from
trait Example {
    // ILLEGAL: no input parameters, so no lifetime to infer the output from.
    // Where does the returned &str come from? The compiler can't tell.
    fn get_str() -> &str;
}
Illegal elision — ambiguous inputs
trait Example {
    // ILLEGAL: two input lifetimes, no &self.
    // Is the output borrowing from s or from t? Ambiguous.
    fn frob(s: &str, t: &str) -> &str;
}

In both cases, you must write explicit lifetimes — which brings us to the next section.

Summary of Elision
  • Rule 1: Each & input gets a unique lifetime.
  • Rule 2: One input lifetime? It goes to all outputs.
  • Rule 3: Method with &self? self's lifetime goes to outputs.
  • If none apply: Write explicit lifetimes yourself.

3. Explicit Lifetime Annotations

When the elision rules can't figure things out, you need to write lifetimes explicitly. Let's cover the syntax and the main use cases.

3.1 The Syntax

Lifetime annotations use a leading apostrophe followed by a name, typically short like 'a:

Lifetime syntax
&i32          // a reference (lifetime elided)
&'a i32       // a reference with an explicit lifetime 'a
&'a mut i32   // a mutable reference with lifetime 'a

// Generic lifetime parameter declared in angle brackets, like type generics:
fn foo<'a>(x: &'a i32) -> &'a i32 { x }
Important Lifetime annotations do not change how long any reference lives. They only describe relationships between lifetimes. The actual lifetimes are determined by the program's structure (scopes, blocks, function calls). Annotations just tell the compiler "these lifetimes are related in this way."

3.2 Functions with Explicit Lifetimes

The classic example is a function that takes two references and returns one of them. The compiler can't know which one you'll return, so you must tell it:

The longest function
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

Here, 'a ties all three references together. The signature says: "The returned reference will live at most as long as the shorter of x and y." This is because both inputs share the same lifetime 'a, so the output is constrained to the intersection of their actual lifetimes.

What 'a means here Using the same 'a for both inputs does not mean x and y must have the same actual lifetime. It means the function's contract is: "I'll return a reference valid for as long as both inputs are valid." At any call site, 'a becomes the shorter of the two actual lifetimes.

3.3 Structs Holding References

If a struct holds a reference (rather than owning the data), it needs a lifetime parameter to ensure the struct doesn't outlive the data it borrows:

Struct with a lifetime
// This struct borrows a string slice — it does NOT own it.
// The lifetime 'a says: "this struct cannot outlive the string it references."
struct ImportantExcerpt<'a> {
    part: &'a str,
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().unwrap();

    // 'excerpt' borrows from 'novel'. If 'novel' is dropped first, this would be
    // a dangling reference. The lifetime 'a prevents that.
    let excerpt = ImportantExcerpt {
        part: first_sentence,
    };

    println!("Excerpt: {}", excerpt.part);
}

3.4 Multiple Lifetimes

Sometimes a struct or function needs different lifetimes for different references. For example, a struct that borrows from two independent sources:

Multiple lifetimes
// Two independent lifetimes — the struct can borrow from two
// different sources with different lifetimes.
struct Context<'a, 'b> {
    config: &'a str,   // borrowed from config source
    input:  &'b str,   // borrowed from input source
}

// A function returning a reference tied to only ONE of its inputs:
fn parse<'a, 'b>(config: &'a str, input: &'b str) -> &'a str {
    // Returns something borrowing from config, not input.
    // Note: output lifetime is 'a, NOT 'b — it's tied to config only.
    config
}

You can also combine lifetimes, generics, and trait bounds in one signature:

Lifetimes + generics + trait bounds
use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");
    if x.len() > y.len() { x } else { y }
}

4. Lifetimes as a Theory of Sets Over Memory

This is the conceptual core that most tutorials skip. Instead of thinking about lifetimes as "annotations on function signatures," think about them as sets of program points — regions of code where a piece of memory is valid. This is the model the Rustonomicon uses, and it unlocks understanding of subtyping, variance, and coercion.

4.1 Lifetimes as Regions

A lifetime 'a defines a region of code — a set of program points (statements, expressions) between where a variable is created and where it's dropped. We can draw this as a set:

Program point: 1 2 3 4 5 6 7 8 9 │ │ │ │ │ │ │ │ │ 'b (x's life): │ │ [████████████] │ │ │ │ │ │ │ x created x dropped │ │ │ │ │ │ │ │ │ │ │ 'a (r's life): │ [████████████████████████████████] │ │ r created r used │ As SETS: 'b = { 3, 4, 5 } (points where x is alive) 'a = { 2, 3, 4, 5, 6, 7, 8, 9 } (points where r is alive/used) Is 'b ⊆ 'a? YES → x's lifetime is contained in r's lifetime But we need 'a ⊆ 'b for r = &x to be safe. It's NOT. → ERROR!

A lifetime is a set of program points. When we say a reference has lifetime 'a, we mean "this reference is valid at all points in the set 'a." The borrow checker's rule is: the data's lifetime set must contain (be a superset of) the reference's lifetime set.

4.2 Subtyping: 'long <: 'short

Here's where it gets interesting. In Rust's type system, lifetimes have a subtyping relationship. The rule is:

'long <: 'short   if and only if   'long completely contains 'short

In set terms: 'long ⊇ 'short (the longer lifetime's region is a superset of the shorter one's). This is the opposite of what many people first guess! A longer lifetime is a subtype of a shorter one.

SUBTYPING RULE: 'long <: 'short ⟺ 'long ⊇ 'short 'long: [████████████████████████████] (bigger region = superset) 'short: [████████████████] (smaller region = subset) Because 'long's region CONTAINS 'short's region, 'long is a SUBTYPE of 'short. Intuition: A value valid for a LONG time is also valid for a SHORT time. "If it lives long enough, it certainly lives long enough for this shorter use."

The practical consequence: you can use a longer-lived reference where a shorter-lived one is expected. For example, a &'static str (lives forever) can be used anywhere a &'a str (lives for 'a) is needed:

Lifetime subtyping in action
fn debug<'a>(a: &'a str, b: &'a str) {
    println!("a = {a:?} b = {b:?}");
}

fn main() {
    let hello: &'static str = "hello";       // lives for the entire program
    {
        let world = String::from("world");
        let world = &world;                   // 'world — a shorter lifetime

        // hello (&'static str) is silently coerced to &'world str.
        // This works because 'static <: 'world (static contains world's region).
        debug(hello, world);
    }
}

4.3 Lifetime Coercion

When the compiler converts a longer lifetime into a shorter one to satisfy a function's signature, that's called lifetime coercion. It happens automatically and silently:

Coercion: 'static → 'a
fn bar<'a>() {
    let s: &'static str = "hi";   // 'static — lives forever
    let t: &'a str = s;           // COERCED: 'static → 'a
                                  // Legal because 'static <: 'a (static outlives everything)
}

Coercion only goes one way: longer → shorter. You can never coerce a shorter lifetime into a longer one, because that would mean claiming a reference is valid for longer than its data actually exists — a dangling reference.

4.4 The Set Intuition — Why It Matters

Thinking in sets gives you a powerful mental model:

ConceptSet Theory ViewPractical Meaning
Lifetime 'aA set of program points"Valid in this region of code"
'a: 'b (outlives)'a ⊇ 'b (superset)"'a's region contains 'b's region"
'long <: 'short'long ⊇ 'short"Longer is subtype of shorter"
CoercionRestrict to a subset"Use a long ref where a short one is needed"
Borrow checkdata ⊇ ref"Data's set must contain ref's set"
The 99% Intuition 'long <: 'short if and only if 'long defines a region that completely contains 'short. 'long may be larger, but that's fine. This simple rule covers 99% of cases. The compiler handles the corner cases automatically — unless you write unsafe code.

5. The 'static Lifetime

'static is a special lifetime that means "valid for the entire duration of the program." It's the longest possible lifetime — its region is the entire program.

'static
// String literals are stored in the binary — they live for the whole program.
let s: &'static str = "I have a static lifetime.";

All string literals have type &'static str because they're baked into the program's read-only data section at compile time. They never get freed.

'static also appears in const and static items:

const and static
// STRING: &'static str  (the 'static is implied for const/static)
const STRING: &str = "bitstring";

struct BitsNStrings<'a> {
    mybits: [u32; 2],
    mystring: &'a str,
}

// BITS_N_STRINGS: BitsNStrings<'static>
const BITS_N_STRINGS: BitsNStrings<'_> = BitsNStrings {
    mybits: [1, 2],
    mystring: STRING,
};
Caution When you get a compiler error suggesting you add 'static, be careful. It's often a sign of an underlying problem (a dangling reference or lifetime mismatch) that should be fixed, not masked. Slapping 'static on everything makes your code inflexible — it forces all references to live forever, which often means you can't borrow local data. Fix the root cause instead.

6. Variance & Subtyping

Now we go deeper. Variance describes how the subtyping relationship of lifetimes (or types) propagates through generic types. If 'long <: 'short, what can we say about &'long T vs &'short T? That depends on the variance of the type constructor.

6.1 The Three Kinds of Variance

Given a generic type F<T> and a subtype relationship Sub <: Super:

VarianceRelationshipMeaning
Covariant F<Sub> <: F<Super> Subtyping passes through unchanged. If Sub is a subtype, F<Sub> is too.
Contravariant F<Super> <: F<Sub> Subtyping is inverted. If Sub is a subtype, F<Super> is the subtype.
Invariant No relationship F<Sub> and F<Super> are unrelated. They must match exactly.

6.2 The Variance Table

Here's how common Rust types behave with respect to their lifetime ('a) and type (T) parameters:

TypeVariance over 'aVariance over T
&'a Tcovariantcovariant
&'a mut Tcovariantinvariant
Box<T>—covariant
Vec<T>—covariant
UnsafeCell<T>—invariant
Cell<T>—invariant
fn(T) -> U—contravariant over T, covariant over U
*const T—covariant
*mut T—invariant

6.3 Why &mut T Is Invariant

This is the most important practical consequence of variance. &mut T is invariant over T. This means you cannot substitute a &mut &'long str where a &mut &'short str is expected, even though 'long <: 'short.

Why? Because allowing it would enable a use-after-free:

Why invariance matters — this is rejected
fn assign<T>(input: &mut T, val: T) {
    *input = val;
}

fn main() {
    let mut hello: &'static str = "hello";
    {
        let world = String::from("world");
        // If this were allowed, 'world' (short lifetime) would be written
        // into 'hello' (which expects 'static). After the block ends,
        // 'world' is dropped — but hello still references it. USE-AFTER-FREE!
        assign(&mut hello, &world);  // ERROR: lifetime mismatch
    }
    println!("{hello}");  // would print freed memory
}

Because &mut T is invariant over T, the compiler refuses to apply any subtyping to the first argument. T must be exactly &'static str, but &world is &'world str — not the same. Rejected. Memory safety preserved.

Contravariance of function arguments Function arguments are contravariant. A function that accepts &'static str can be used where a function accepting &'a str is expected (it accepts more, so it's safe). But the reverse is not allowed — a function accepting only short-lived references can't be used where one accepting long-lived references is needed.

7. Lifetime Bounds & HRTB

7.1 'a: 'b — Outlives Bounds

You can write 'a: 'b to say "lifetime 'a outlives lifetime 'b" (i.e., 'a ⊇ 'b). This lets you assign a longer reference to a shorter one:

Outlives bounds
fn f<'a, 'b>(x: &'a i32, mut y: &'b i32)
where
    'a: 'b,   // 'a outlives 'b
{
    y = x;                    // OK: &'a i32 is a subtype of &'b i32 because 'a: 'b
    let r: &'b &'a i32 = &&0; // OK: &'b &'a i32 is well-formed because 'a: 'b
}

7.2 Implied Bounds (T: 'a)

The compiler automatically infers some lifetime bounds. If you have &'a T, the compiler infers T: 'a — meaning "T doesn't contain any references shorter than 'a." This is called an implied bound:

Implied bounds
// The compiler infers T: 'a from the reference type &'a T.
fn requires_t_outlives_a<'a, T>(x: &'a T) {
    // This compiles because T: 'a is implied by &'a T.
    requires_t_outlives_a_not_implied::<'a, T>();
}

fn requires_t_outlives_a_not_implied<'a, T: 'a>() {}

// But without the &'a T, T: 'a is NOT implied:
fn not_implied<'a, T>() {
    // ERROR: T: 'a is not implied by the signature.
    // requires_t_outlives_a_not_implied::<'a, T>();
}

The same applies to structs and enums — the compiler infers bounds from fields:

Inferred bounds in structs
struct Struct<'a, T> {
    // This requires T: 'a to be well-formed — inferred automatically.
    field: &'a T,
}

enum Enum<'a, T> {
    // T: 'a is required even when only using OtherVariant.
    SomeVariant(&'a T),
    OtherVariant,
}

7.3 Higher-Ranked Trait Bounds (HRTB)

Sometimes you need a function or closure to work with references of any lifetime, not a specific one. This is what Higher-Ranked Trait Bounds (HRTBs) are for. The syntax is for<'a>:

HRTB — for<'a>
// "F is a function that works for ANY lifetime 'a"
impl<F> Closure<F>
where
    for<'a> F: Fn(&'a (u8, u16)) -> &'a u8,
{
    fn call(&self) -> &u8 {
        (self.func)(&self.data)
    }
}

fn do_it(data: &(u8, u16)) -> &u8 { &data.0 }

fn main() {
    let clo = Closure { data: (0, 1), func: do_it };
    println!("{}", clo.call());
}

Without for<'a>, the compiler would need to pick one specific lifetime for 'a, which wouldn't work because the closure needs to accept references with whatever lifetime the caller provides. HRTBs say "this works for all lifetimes."

HRTBs also appear in function pointer types and trait objects:

HRTB in types
// Elided form:
type FunPtr1 = fn(&str) -> &str;
// Expanded form with HRTB:
type FunPtr2 = for<'a> fn(&'a str) -> &'a str;

// Trait objects:
type FunTrait1 = dyn Fn(&str) -> &str;                // elided
type FunTrait2 = dyn for<'a> Fn(&'a str) -> &'a str;  // expanded

8. Common Patterns

8.1 Iterators & PhantomData

Iterators that borrow from a collection need a lifetime parameter. But sometimes the lifetime isn't directly used in a field — it's only logically associated. In that case, you use PhantomData to tell the compiler about the relationship:

Iter with PhantomData
use std::marker;

// An iterator over &'a [T]. The raw pointers don't carry the lifetime,
// so we use PhantomData to tell the type system about it.
struct Iter<'a, T: 'a> {
    ptr: *const T,
    end: *const T,
    _marker: marker::PhantomData<&'a T>,  // "this struct logically holds &'a T"
}

// PhantomData consumes no space but simulates a field for static analysis.
// This gives correct variance (covariant over 'a and T) and drop checking.

The Drain iterator (which removes elements from a Vec while borrowing it) uses the same pattern:

Drain iterator
use std::marker::PhantomData;

pub struct Drain<'a, T: 'a> {
    vec: PhantomData<&'a mut Vec<T>>,  // borrows the Vec mutably
    iter: RawValIter<T>,
}

impl<'a, T> Iterator for Drain<'a, T> {
    type Item = T;
    fn next(&mut self) -> Option<T> { self.iter.next() }
}

impl<'a, T> Drop for Drain<'a, T> {
    fn drop(&mut self) {
        // Drain remaining elements on drop — safety mechanism.
        for _ in &mut *self {}
    }
}

8.2 Self-Referential Structs & Pin

When Rust compiles async blocks into state machines, the resulting structs can be self-referential — one field holds a reference to another field in the same struct. Moving such a struct would invalidate the internal reference. The Pin type solves this:

Pin and the Future trait
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    // Pin<&mut Self> guarantees the future won't be moved in memory.
    // This is essential for self-referential async state machines.
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

Pin wraps a pointer and guarantees the pointed-to value won't move. This keeps internal references valid. Most types are Unpin (safe to move even when pinned), but async-generated futures are !Unpin and require pinning.

8.3 Builder / Type-State Pattern

Lifetimes work naturally with the type-state pattern, where the compiler enforces state transitions at compile time. Methods that return references from &self benefit from elision Rule 3:

Type-state with lifetime elision
pub struct Post { content: String }
pub struct DraftPost { content: String }
pub struct PendingReviewPost { content: String }

impl Post {
    pub fn new() -> DraftPost { DraftPost { content: String::new() } }

    // &self -> &str uses Rule 3: output gets self's lifetime.
    // No explicit lifetime needed!
    pub fn content(&self) -> &str {
        &self.content
    }
}

impl DraftPost {
    pub fn add_text(&mut self, text: &str) {
        self.content.push_str(text);
    }
    // Consumes self, transitions to next state:
    pub fn request_review(self) -> PendingReviewPost {
        PendingReviewPost { content: self.content }
    }
}

impl PendingReviewPost {
    pub fn approve(self) -> Post {
        Post { content: self.content }
    }
}
Why this is elegant The type-state pattern uses ownership (consuming self) to enforce transitions. You can't call content() on a DraftPost because the method simply doesn't exist on that type. Invalid states are impossible at compile time. And lifetime elision Rule 3 handles the borrowing automatically — no explicit lifetimes needed.
